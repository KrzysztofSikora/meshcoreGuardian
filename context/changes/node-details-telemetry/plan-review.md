| 1 | major | Grounding / Phasing | *Findings* says "Only the SQLite implementation of `DiagnosticRunRepository` exists ... so new port methods need no fake". That is wrong: `apps/mobile/src/application/diagnostics/run-controller.int.test.ts:40` has `class MemoryRuns implements DiagnosticRunRepository`. Phase 2 adds `recentForNode` and `lastRespondedAt` to the port (`packages/domain/src/diagnostics/run.ts`), so `pnpm typecheck` fails at the end of Phase 2 unless that file changes too, and Phase 2's file list does not include it. | Add `run-controller.int.test.ts` (stub the two methods on `MemoryRuns`) to Phase 2's files and correct the finding. `run-controller.ts` is a mutation target, but this touches only its test. |
| 2 | major | Design / Failure paths | The Phase 1 contract is "`checkSeq` = index in `checks`". D-3 backfill "selects responded status/telemetry checks without a sample ... using the same `samplesFromChecks`". If the backfill passes only the filtered checks (that is what it selects), the index is not the stored `seq`. Samples then get the wrong `check_seq`, or the composite FK `(run_id, check_seq) → diagnostic_checks` fails. The `NOT EXISTS` filter also makes a run's check list partial on a re-run after a crash. | Choose one: (a) the backfill loads all checks of each affected run in `seq` order and filters the output by the missing `(run_id, seq)`, or (b) `samplesFromChecks` takes `(seq, check)` pairs. Add a backfill test where the responded telemetry check is at seq 2 after a login at 0 and a status at 1, with the status sample already present. |
| 3 | major | Lessons / Failure paths | The lesson "When a filter narrows data to 'the last operation', test a partial last operation from the same source" applies to D-7, because "latest telemetry" is "the samples of the newest run that has any sample". When the newest run has a status sample but its telemetry check got `NO_RESPONSE`/`UNSUPPORTED`, the older run's telemetry disappears. The plan does not say what the telemetry group shows then, and no test covers it. Phase 2 tests only "a later run without samples does not hide it". | Define the display for a missing source group in the chosen run (for example "No telemetry in this run" plus the check result, not "N/A" values and not a silently missing group). Add a repository test and a presenter test for "newest run: status responded, telemetry no response". |
| 4 | minor | Failure paths | D-3: "A check whose stored evidence fails to parse is skipped, not fatal", but the plan says nothing about other errors. `openGuardianDb` (`apps/mobile/src/platform/sqlite/open-guardian-db.ts:9`) is the single DB opener. A SQL or constraint error in the backfill would reject it, and every storage feature would fail at start because of derived data. | Catch backfill errors in `openGuardianDb` (or inside the backfill) and continue, and test that a failing backfill still returns a working driver. |
| 5 | minor | Design | Samples are written in the run's transaction and the table has `CHECK (uptime_s >= 0)` and scope/value pairing. A derived value that violates a CHECK then loses the whole run (Phase 2 even tests "a failing sample insert rolls back the run"). The run is the primary record. The samples are derived and can be rebuilt by the backfill. | Make `samplesFromChecks` total: it maps an out-of-range value to null instead of relying on the CHECK to abort `save`, and a unit test covers that. Keep the rollback test as a guard. |
| 6 | minor | Design | `telemetry_samples.device_id` duplicates `diagnostic_runs.device_id`. No constraint keeps them equal. | Either drop `device_id` and join through `diagnostic_runs` (indexed on `(device_id, finished_at)`), or keep it for S-07 and assert in a test that save and backfill write the run's device. |
| 7 | minor | Phasing / e2e | D-13 asserts "a 'Responded' run row" on the node screen. The diagnostic panel there already shows "Responded" (`diag-responded.yaml:12-14`), so the assertion would pass even with no run row. The row is also at the bottom of the `FlatList` below the edit cards, so it needs `scrollUntilVisible`. | Assert on text or an id that only the row has (for example its time and duration, or a `testID`), and reach it with `scrollUntilVisible` (the lesson on scroll assertions). |
| 8 | minor | Agent decisions | D-5 "0 mV → null" is marked `costly` and `UNVERIFIED`. That is correct, but it changes stored meaning on an inference. | Keep it, but list it under *Human checks* or *Risks* as something to confirm on a node without a battery ADC, and put it in the PR's reviewer list. |

## Decisions the PR reviewer should look at
- D-5: 0 mV is stored as null (N/A), an inferred meaning that is persisted.
- D-6: the `last_hop` scope and the wording "last hop into the node" are `UNVERIFIED`, and they settle FR-07 AC3.
- D-3: the backfill runs at every app start and writes derived rows (see findings 2 and 4).
- D-8: FR-08 AC2 ships without the voltage chart (`[REVIEW]` deviation already logged).

## What is good
- The traceability is clear: each AC maps to unit, integration and e2e tests, and the roadmap's "migration from v1" acceptance is tested explicitly.
- One domain mapping is shared by save and backfill, and samples are written atomically in the run's transaction.
- The citations hold up. The 12 LPP types match `cayenne_lpp.js`, timing matches `mesh-client.ts:251,271`, the screen structure matches `screen.tsx` and `node/[id].tsx`, and the schema matches `0002_diagnostics.sql`.
- The plan spots the `FlatList`-in-`ScrollView` trap and applies the lesson on e2e height and shared lists in Phase 4.
- The scope stays tight: the chart, export and paging are out, and no new radio requests are added.
