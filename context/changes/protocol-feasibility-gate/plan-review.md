## Decisions the PR reviewer should look at
- D-4: what is redacted from committed fixtures (BLE PIN, location, chat names; repeater/room data kept verbatim). Privacy- and secret-relevant, and it can't be undone after a push.
- D-3: fixture format, read by S-02's `FakeTransport` and every fixture test. Re-capturing needs radio TX.
- D-6: the PASSED/FAILED rule, with a room server as the target and no INCONCLUSIVE verdict.

## What is good
- The library claims I spot-checked hold, apart from findings 5 and 6: `int8` `outPathLen`, the 6 "reserved" device-info bytes, raw `statusData` in the push, no 0x86 handler (unhandled → `console.log`), dynamic `serialport`/`net` imports, and `@noble/curves` + `serialport` dependencies.
- It catches the BLE PIN inside device-info frames before anything is committed.
- The radio budget is enforced in code and tested with a fake clock (TR-23). A `handshake` scenario checks the tool without LoRa TX.
- Scope is tight: `MeshClient`, Zod and app transports are explicitly deferred to the slices that own them (D-9). Lint layering for `tools/**` comes with tests.
- Each phase leaves the gates runnable. Only phase 5 needs hardware, and it says so, with a `[STUCK]` path.
