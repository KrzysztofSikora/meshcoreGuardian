## Decisions the PR reviewer should look at
- D-11: the 5 s idle bound, which conflicts with the 4.9 s gap in the real fixture (finding 1). Because D-8 stores nothing on a timeout, this decides whether syncs succeed on a busy mesh.
- D-4: whether the expo transaction opens a second connection, which affects lock errors on user edits and PRAGMA scope (finding 2).
- D-7: whether `lastMod` is a fair "last heard" (`UNVERIFIED`, and visible to users).
- D-9 (costly): `in_contacts` is global, not stored per companion. It is fine while there is one companion, but it is a schema choice S-04 builds on.

## What is good
- The citations are grounded. The fixture checks out: 350 contacts with 306/14/30 types, `chat-1` at seq 16, `chat-2` at seq 25, the room at seq 35, and `PL-KR-WRBL-RPT` at seq 8. So do the `decodeFrame` shapes, the meshcore.js `sendCommandGetContacts` encoding and the expo-sqlite API surface.
- D-8 marks nodes as missing only after a complete sync whose count matches. That is a careful answer to TR-15 and the roadmap's "keep history" rule, and the integration tests cover each merge rule.
- The reported and user values sit in separate columns (D-1), and Dashboard membership is derived (D-10). That keeps "user wins, protocol shown" free of stored state that could drift.
- The layering matches `tech-stack.md`: the domain owns the port, storage implements it, and the adapter returns `ContactReport` without assigning a role. D-17 keeps `node:sqlite` out of the app in line with the lint rules. The plan applies the lessons on idempotent `load()`, port error paths and minimal port doubles.
- Out of scope is explicit, and the follow-ups (`since`, `0x90`, remove from dashboard) are recorded as deviations instead of being pulled into this change.
